- [x] **Family Controls authorization not handled** (was a release blocker) — was: request at launch + swallow errors, so a denied/revoked/restricted user saw a working-looking app that enforced nothing (also surfaced as the spurious "selection was reset" toast). **Implemented:** `AccessController` now tracks `AuthorizationCenter.authorizationStatus` (live + re-read on scenePhase); when not `.approved`, `ContentView` shows `PermissionDeniedView` in place of the app card and disables the arm/quick CTAs. **There is no per-app Screen Time toggle in iOS Settings**, but re-calling `requestAuthorization` re-shows the system prompt — so the denied view is a single **"Allow access"** button that re-requests directly (no Settings trip). `UNPLUG_SKIP_FC` bypasses the gate. Strings localized ×10. **Verified on device** (deny → denied UI → tap Allow → prompt reappears → approve → returns to app list). Merged to `main`. Note: revoking auth in system settings while the app is running doesn't update `authorizationStatus` until next cold launch (Apple bug) — acceptable.

Moved off-main onto a serial queue in `Schedule` (UI/`Model` mutations stay on main; values captured before dispatch). ## QA pass — features 3, 4, 9 (2026-07-25)

Full report in `qa/findings.md`; method and its limits in `qa/workflow-notes.md`; manual test script in `qa/device-matrix.md`. 19 confirmed findings, 3 uncertain, 1 refuted. **No fixes applied** — this was a find-and-prove pass only. Fix order below is by consequence, not by effort.

- [ ] **V22 — ship-blocker, cheapest fix on the list.** `PricingConfig.cutoverDate` is 2026-06-25, a month in the past while 1.3 is still unshipped, so every customer who paid $0.99 since then is *not* grandfathered and will be asked to pay again. Zero users affected today; deterministic for the whole cohort the day 1.3 ships unchanged, and the cohort grows one day per day of slip. Proven red in `PricingBoundaryTests`. **Fix before submitting 1.3** — it interacts directly with the v1.3 release sequencing item below.
- [ ] **V07 — breaks the core promise (bypass).** The monitor extension's `intervalDidEnd` treats `daily` and `hourly` identically (`DeviceActivityMonitorExtension.swift:74-78`), so a one-hour quick block *ending* clears the shields of a concurrently active nightly block. Found independently by 3 lenses. Needs device confirmation.
- [ ] **V01 — silently substitutes "now" for the user's chosen end time.** Dragging the end handle to the axis tick labelled 24:00 yields `bySettingHour: 24` → nil → `?? Date()` (`ScheduleRangeSlider.swift:41`; confirmed by executing it in 4 time zones). Fires on the gesture the UI advertises; in block mode with `now < start` it can register a ~24h unstoppable block **with no risk confirmation**.
- [ ] **V05 / V02 — the risk gate cannot see wrapping windows.** `ScheduleMath.freeMinutes` disagrees with a brute-force oracle on **1,036,080 of 2,073,600** windows — every single one that wraps midnight, i.e. every overnight block, which is the app's core use case. Proven red in `ScheduleMathBoundaryTests`. V02 adds that the window silently shifts an hour at every DST transition.
- [ ] **V18 / V17 — a paying legacy user can be told "Trial ended".** Grandfathered access is unpersisted derived state, so one failed `AppTransaction` fetch demotes them to expired, and Restore then asserts "No previous purchase found" even when `AppStore.sync()` merely failed offline. This is the refund-request path.
- [ ] **V21 — sits on the app's own conversion path.** Buying the unlock mid-window does not restore enforcement for the window already in progress; "common among users who convert after trial expiry".
- [ ] **V11 / V14 — the lock-while-active UI does not engage.** The app never observes the extension's `inside_interval` write, so a block starting while the app is foregrounded shows the wrong status and an inert CTA. Frequency: common.
- [ ] **V20 / V23 — revenue leaks.** The enforcement gate is only recomputed while foregrounded (never reopen the app and the trial never expires), and an expired trial is fully restored by moving the device clock backward (proven red).
- [ ] Remaining confirmed: V04, V06, V09, V13, V15, V16, V19, V24. Uncertain and settleable on-device: V12, V13, V25.
